# Edge Cases — No Donuts

A living log of edge cases to validate together. Each has a **decision** (or `OPEN`) and a **status**.

**Status:** `OPEN` (needs discussion) · `DECIDED` (policy set) · `IMPLEMENTED` (in code + tested)

| # | Edge case | Decision | Status | Owner |
|---|---|---|---|---|
| EC-01 | **On a video call** (another app holds camera) | Try multi-client shared frames; if none, assume PRESENT and don't lock — **bounded** by `maxCallAssumedPresentSeconds` (default 30 min). After that many CONTINUOUS busy-no-frames seconds the assume-present window expires and the engine escalates to absence, so a call app left running unattended eventually runs the normal grace→lock path instead of staying unlocked forever. The cap is NOT the wall-clock time-to-lock: once it expires the engine only *begins* counting absence, so the effective unlock ceiling is `maxCallAssumedPresentSeconds` + the absence consensus (`consecutiveAbsentTicksToLock` ticks) + `graceSeconds`. A genuinely long call with no obtainable frames WILL be locked at the cap — an accepted, bounded fail-open tradeoff (tunable). Any non-busy outcome (real present/absent frame, suspend, unavailable) resets the window — including the production `sessionSuspended()` lock/unlock path, so a fresh call after an unlock starts a clean window rather than re-escalating on a stale one. See [ADR-0003](adr/0003-camera-in-use-policy.md), ND-033. **ND-032 (explicit multi-client shared-frame acquisition) is closed as not-needed on macOS:** the OS shares the camera across clients, so a busy device normally still delivers frames to our session (→ normal detection); only the busy-no-frames case uses the assume-present fallback above. | IMPLEMENTED | blart/homer |
| EC-02 | **Screen already locked / display asleep / session inactive** | Event-driven `SessionStateMonitor` (ND-013, [ADR-0009](adr/0009-session-suspend.md)) pauses the loop and stops the camera while the screen is locked, the display is asleep, or the session is not on the console; resumes both on unlock/wake. On suspend the app calls `PresenceEngine.sessionSuspended()`, which resets absence accounting so resume can't false-lock (the in-tick `.suspended` capture path is a backstop). **Resume robustness:** our lock mechanism (SACLockScreenImmediate / CGSession `-suspend`, ADR-0010) does **not** reliably post `com.apple.screenIsUnlocked`, so relying only on notifications left the app stuck "locked" after unlock. The monitor therefore also runs a low-frequency **safety-net poll** (~2s) that re-reads the authoritative `CGSession`/`CGDisplay` state and fires on the real transition — a missed lock/unlock event self-heals within ~2s. | IMPLEMENTED | blart/homer |
| EC-03 | **Stranger sits down, enrolled user absent** | **Identity (ND-021–024/ND-034, [ADR-0012](adr/0012-local-identity-featureprint.md)):** once the user has enrolled, a detected face is embedded and cosine-matched against the enrolled reference vectors; a face that doesn't clear the threshold returns `.strangerOnly` → the engine treats it as absence → locks after grace. A non-matching face NEVER counts as present. **Before enrollment** the app falls back to presence-only (any face = present). **Durable fix in progress ([ADR-0014](adr/0014-coreml-face-embedding-model.md), ND-021):** the shipping embedder is still Apple `VNGenerateImageFeaturePrint` — a *general* (image-similarity, not face-identity) feature print, so a determined look-alike ("Marco") can still false-accept. Phase 1 landed the real fix's scaffolding — a model-agnostic descriptor, a `CoreMLFaceEmbedder` (FaceNet/VGGFace2, 512-dim), and embedding-versioning that forces re-enrollment on a model swap (no cross-model vector compares). **The structural EC-03 guarantee is only restored once that Core ML face model is bundled and its threshold re-tuned (Phase 2, blocked on the model file);** until then the caveat stands (lenient/un-tuned separation). | IN PROGRESS — enforced after enrollment; general feature print today (look-alikes may pass), Core ML face-identity model landing via ND-021 Phase 2. **ND-073:** if identity falls back to presence-only (model mismatch/missing model, or enrollment deleted outside the app, detected via a non-secret UserDefaults marker), the app says so loudly: menu header, orange glyph, repeating notification, "Re-enroll (required)" item. Never silent. | homer/wiggum/cooper |
| EC-04 | **User present but looking away / turned head** | Detection may miss the face briefly; the grace period + consecutive-absent debounce (ND-030, IMPLEMENTED: `graceSeconds` + `consecutiveAbsentTicksToLock`) absorbs short gaps. Tune thresholds. **Note (ND-017):** the menu indicator now flips to `.absent` ("away") on the FIRST no-face tick (responsive), while the LOCK still waits for the full consensus + grace window. So a brief glance-away can show "away" transiently in the menu without ever locking — the responsive status and the lock decision are decoupled. | OPEN | cooper/homer |
| EC-05 | **Poor lighting / backlight / glasses / hat / mask / camera orientation** | Affects detection + match. Need robust model + threshold; surface "can't see you" status. **Orientation:** the Vision source orientation defaults to `.up` (correct for the built-in landscape-upright, now-non-mirrored camera) but is overridable via `defaults write com.nodonuts.app visionOrientation <1–8>` for atypical/external cameras, applied consistently to detection AND the crop so matching stays valid. **Threshold:** `matchThreshold` is tunable via `defaults write com.nodonuts.app matchThreshold <0<t<1>` (0 and 1.0 are rejected — 0 ≈ fail-open, 1.0 unreachable → lockout); the live match score is logged to help pick a value (ND-024). **ND-076 (2026-09-24):** the threshold now lives with the model: `matchThreshold.<model version>` (FaceNet default 0.50, range 0.40–0.90; Vision 0.60, 0.40–0.95). Out-of-range values are rejected, not clamped. The old global `matchThreshold` key is dropped once at launch. | OPEN | cooper |
| EC-06 | **Multiple faces in frame** (user + colleague) | If the enrolled user matches any face → PRESENT (v1.1: the embedder currently evaluates the largest face; multi-face scan-all is a follow-up). Shoulder-surfing (user present but a stranger also watching) is out of scope for v1. | PARTIAL (single/largest face) | cooper/homer |
| EC-07 | **External monitor, lid closed (clamshell)** | Built-in camera unavailable → `capture()` returns `.unavailable` → engine surfaces honest `cameraUnavailable` status and does NOT lock (no fail-open; this is now real, not masked by a fake recognizer). User isn't locked out when the only camera is gone. A "not protecting" local notification now fires on entry + repeats ~5 min while unavailable, clearing on recovery (ND-045, `NotProtectingNotifier`). | IMPLEMENTED | blart/homer/krusty |
| EC-08 | **Camera permission denied / restricted (MDM)** | `capture()` returns `.unavailable` (denied/restricted or no device); engine surfaces honest `cameraUnavailable` status and does NOT lock. No silent fail-open. krusty owns the prompt/remediation UX; a "not protecting" local notification fires on entry + repeats ~5 min while unavailable (ND-045). | IMPLEMENTED | blart/homer/krusty |
| EC-09 | **No camera at all / camera hardware error** | Same policy as EC-07/EC-08: `.unavailable` → `cameraUnavailable`, do NOT lock (never hard-lock the user out when we can't see). Honest visible status + the ND-045 "not protecting" notification. | IMPLEMENTED | blart/homer |
| EC-10 | **Recognition error / model timeout on a tick** | Conservative HOLD (bounded): a transient `.error` tick neither advances nor resets the absence consensus — no markAbsent (no lock-storm) and no markPresent (no false-unlock); state + counters left untouched until the next clean reading. The 3-tick absence consensus (`consecutiveAbsentTicksToLock`) further damps single-frame glitches. **The hold is bounded:** after `maxConsecutiveErrorsBeforeAbsent` (default 3) CONSECUTIVE errors the engine escalates — it treats the tick as absence (markAbsent), so a wedged recognizer runs the normal grace→lock path and locks rather than holding unlocked forever (no indefinite fail-open). Any clean reading resets the error streak. | DECIDED | homer |
| EC-11 | **User briefly leaves and returns within grace** | No lock; reset cleanly on re-detect. **Note (ND-017):** the menu indicator flips to `.absent` ("away") on the FIRST no-face tick (responsive), but the LOCK waits for the consensus + grace window — so a brief leave-and-return shows "away" transiently in the menu and then clears back to present on re-detect, never locking. New default timing: effective walk-away→lock ≈ consensus (5 × 1s tick) + grace (5s) ≈ 10s. | DECIDED | homer |
| EC-12 | **Photo / phone screen held up to spoof** | Basic anti-spoofing shipped (ND-041): a variance-of-Laplacian texture/liveness score on the face crop (`FaceLiveness.swift`) flags clearly flat reproductions. CONSERVATIVE by design — only checked on the ENROLLED path AFTER a threshold match, only flags when the score is strictly below a **tunable** floor (`resolvedSpoofTextureFloor`, `defaults write com.nodonuts.app spoofTextureFloor <n>`, default 12.0) → `.strangerOnly` (locks). The score is measured on the INNER face region (not the padded embedding crop), so a live user against a plain background isn't diluted below the floor; it errs toward LIVE on any ambiguity/extraction failure and never false-locks the real user. ON by default (toggle `antiSpoofEnabled`); texture compute is skipped entirely when the toggle is off. **v1 is NOT hardened:** a sharp high-resolution print or a high-DPI screen at the right size can still pass; the floor needs on-device tuning; motion/blink liveness is future work. **KNOWN GAP (ND-072):** anti-spoofing is currently INACTIVE on the Core ML face-embedder path (ADR-0014) — `CoreMLFaceEmbedder` returns the `.infinity` live/unknown sentinel instead of a real texture score, so the gate never trips there; the check only runs on the Vision fallback path. With the Core ML embedder active, a flat photo of the enrolled user is accepted. Tracked as ND-072 (wire the shared texture score into the Core ML path + re-tune the floor for that crop pipeline). | PARTIAL | wiggum/cooper |
| EC-13 | **Laptop sleep / wake, lid open/close** | Handled via `SessionStateMonitor` (ND-013, [ADR-0009](adr/0009-session-suspend.md)): the loop pauses + camera stops on sleep and resumes on wake. On suspend the app calls `PresenceEngine.sessionSuspended()`, which resets absence accounting, so an absence in progress when the Mac sleeps cannot cause a grace-less false lock on wake — the next absence episode rebuilds the full consensus + grace. | DECIDED | blart/homer |
| EC-14 | **Fast user switching / multiple accounts** | Out of scope for v1. Partial mitigation: `SessionStateMonitor` suspends the loop + camera when this session is **not on the console** (`kCGSSessionOnConsoleKey == false`), so we don't run against the login window or another user's session (ND-013). Full multi-account behavior (per-user enrollment, etc.) remains out of scope. | OPEN | homer |
| EC-15 | **App paused by user, then walks away** | Respect pause; don't lock. Pause is a first-class "enforcement off" reason in the single gate ([ADR-0011](adr/0011-enforcement-gating.md)): pausing stops the loop **and turns the camera off** (honest "not watching"), and the menu bar shows a paused state. Options: **15 min** / **1 hr** (auto-resume via timer) / **until I resume** (indefinite). Pause is **in-memory only** — a relaunch/reboot comes back protecting (safe default). ND-035. | IMPLEMENTED | krusty/homer |

New default timing: effective cover→lock ≈ consensus (5 × 1s tick) + grace (5s) ≈ 10s. | DECIDED | blart/homer |

| EC-19 | **Screen-lock request reports success but may not have locked** | The lock **no longer needs Accessibility** ([ADR-0010](adr/0010-screen-lock-no-accessibility.md), supersedes ADR-0006). It is a layered, no-Accessibility mechanism: **(1)** `SACLockScreenImmediate` (resolved at runtime via `dlopen`/`dlsym` from `login.framework`, no link-time dependency), then **(2)** `CGSession -suspend` as a public fallback (login window). `lock()` is **`async`** (`await locker.lock()`) and its verify poll uses `Task.sleep`, so the presence engine's main actor is **never blocked** while a lock is pending. `lock()` **confirms via CGSession** before returning `true`: the screen counts as locked if `CGSSessionScreenIsLocked` is true OR the session is not on the console (`kCGSSessionOnConsoleKey == false`, how `-suspend` presents), read defensively (Bool/NSNumber; on-console signal only trusted when the key is present). If neither mechanism achieves a confirmed lock, `lock()` `os_log`s a warning and returns `false` → engine shows honest `lockFailed`; do **NOT** fail open, and **no stuck fake `.suspended`**. The prior osascript/Ctrl-Cmd-Q path was unreliable (esp. ad-hoc-signed builds) and needed Accessibility — removed. **FUS caveat:** `kCGSSessionOnConsoleKey == false` is ambiguous — it can also mean fast-user-switched-away, not password-locked. It's safe as a lock signal here because `lock()` only runs while ON console (`SessionStateMonitor` pauses the loop off-console, ND-013 / EC-14), so at verify time off-console reliably means our own `CGSession -suspend` succeeded. **Timing:** `lock()`'s verify poll shares ONE ~3s deadline across both mechanisms (SAC then CGSession use the *same* budget, not 3s each), and the poll is cancellation-aware (no CPU busy-spin if the task is cancelled). **2026-09-24 (ND-058/ND-074):** the `CGSession` tool is gone on macOS 27. Fallback (2) is now `SACSwitchToLoginWindow`, from the same `login.framework`, and gives the same off-console verification. A launch and on-wake **self-test** resolves both symbols without calling them; if neither resolves, the app shows a persistent "can't lock the screen" warning plus a repeating notification instead of failing silently at the first walk-away. Each lock logs which mechanism confirmed it. **Lock-failed retry and alarm (ND-054/ND-079, 2026-09-24):** if a lock fails while the user is still away, the engine retries with backoff (10s → 20s → 40s → 60s, then every 60s) until the lock succeeds or the user returns. Each failure posts a `nd.lockFailed` notification with sound, and the menu shows "couldn't lock (retrying)". A manual "Lock now" still in flight at grace expiry no longer uses up the auto attempt (ND-079). | DECIDED (verified) | wiggum/homer |

| EC-20 | **On a user-trusted Wi-Fi network** (e.g. home) | Don't enforce while connected to a network the user has explicitly marked trusted (ND-036, [ADR-0011](adr/0011-enforcement-gating.md)). Trusted-network is a first-class "enforcement off" reason in the single gate: it stops the loop **and turns the camera off**, and the menu bar shows a distinct "paused (trusted Wi-Fi)" state. The trusted list holds SSIDs, managed via a checkable menu item for the current network, persisted locally (UserDefaults) — never transmitted. Reading the SSID (CoreWLAN) needs **Location** (when-in-use), requested lazily on first trust; Location is used only to read the SSID (no coordinates). **Fail-safe:** if the SSID can't be read (Location denied/unavailable, no Wi-Fi), the network is treated as **untrusted** → enforcement stays ON. Priority: an already-locked/asleep session and an explicit user pause both take precedence over trusted-network in the display state. | IMPLEMENTED | krusty/homer |

| EC-21 | **External / virtual camera (DAL device) rejects a fixed capture frame rate** | Some cameras — external UVC webcams, Continuity Camera, virtual cams — are exposed as `AVCaptureDALDevice`, and setting `activeVideoMin/MaxFrameDuration` on them throws an Objective-C `NSException` (which Swift cannot `try/catch`) → the app aborts on launch. Fixed by wrapping the frame-duration set in an ObjC `@try/@catch` shim (`ObjCExceptionCatcher`, used by `CameraController.ensureConfigured()`): if the device rejects the fixed ~1 fps, we log and continue at the device's default rate (non-fatal) rather than crashing. The CMTime is also clamped to the format's `[minFrameDuration, maxFrameDuration]` defensively. Duty-cycle/power tuning of the fallback rate stays tracked in ND-042. | IMPLEMENTED | blart |

| EC-22 | **Multi-display: menu-bar icon only shows on the active display** | The status-item glyph must be a **STATIC** image — either a plain template (adaptive, monochrome) or a colored image with the tint **baked into the pixels**. A runtime-tinted status button (setting `button.contentTintColor` to a non-nil color) draws only on the **currently-active display's** menu bar and is NOT replicated to inactive displays' menu bars, so on a multi-monitor setup the icon appears to vanish (or renders black) everywhere except the active screen — a trust hazard, since the app must always be visible. Fixed in `MenuBarController.render(state:)` (ND-071): never set a non-nil `contentTintColor`; for tinted states bake the color into a non-template symbol via `NSImage.SymbolConfiguration(paletteColors:)` (with a `lockFocus`/`.sourceAtop` fallback), and leave nil-tint states (starting/away/locked) as plain adaptive templates. Confirmed on-device: colored glyph now renders on every display's menu bar simultaneously. | IMPLEMENTED | krusty |

| EC-23 | **Two app instances at once** (LaunchAgent + login item, or a manual `open -n`) | Two copies each ran a camera session, a presence loop and a status item: duplicate glyphs, competing camera clients, duplicate locks. launchd does NOT merge the two launch mechanisms. **Fix (ND-083):** `SingleInstance` takes an exclusive `flock` on `~/Library/Application Support/NoDonuts/instance.lock` before any camera or UI setup. A second copy exits 0 (so the LaunchAgent's `KeepAlive SuccessfulExit=false` doesn't respawn it). The kernel drops the lock on exit or crash, so there is no stale lock. Any other lock-file error → continue (never block protection). Choosing one launcher per install is still open (ND-053/ND-111). | IMPLEMENTED | krusty/gordon |
